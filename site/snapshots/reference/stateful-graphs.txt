Reference · LangGraph Stateful graphs The four ideas, the minimal graph, what a checkpoint does and does not protect, and the decision rule for adopting any of it. Compressed from Lesson 15. Versions and quotes checked against the docs on 2026-08-10 — langgraph 1.2.10 . The one-sentence definition An agent described as a state graph: one typed state object, nodes that are plain functions returning updates to it, edges that decide what runs next — and, with a checkpointer attached, the state written down after every node so the run can pause, crash, rewind and resume. LangChain’s own docs : “you don’t need to use LangChain to use LangGraph” ; it is “very low-level, and focused entirely on agent orchestration.” The four ideas Idea What it is Gotcha State A TypedDict . Nodes return a partial dict; the runtime merges it. Without a reducer, a returned field overwrites . Annotated[list, add_messages] is what makes it append. Node def f(state) -> dict . Ordinary Python; your own SDK calls go straight in. No checkpoint exists inside a node. It is the unit of atomicity you get, and the only one. Edge Static add_edge(a, b) , or add_conditional_edges(a, router) where the router returns the next node’s name . The router is where your if tool_calls: … else: break went. The model never sees the graph. Checkpointer + thread_id Saves state after every node under a thread id. The only thing here a while loop can’t do. InMemorySaver dies with the process — useless for the thing you adopted it for. Use a file or a database. The minimal graph from typing import Annotated, TypedDict from langgraph.graph import StateGraph, START, END from langgraph.graph.message import add_messages from langgraph.checkpoint.sqlite import SqliteSaver # pip install langgraph-checkpoint-sqlite import sqlite3 class S(TypedDict): messages: Annotated[list, add_messages] # reducer: append, don't overwrite def agent(state: S) -> dict: # your existing model call, unchanged reply = client.chat.completions.create(...) return {"messages": [reply]} def tools(state: S) -> dict: ... return {"messages": [result]} def route(state: S) -> str: # returns a NODE NAME return "tools" if state["messages"][-1].tool_calls else END b = StateGraph(S) b.add_node("agent", agent); b.add_node("tools", tools) b.add_edge(START, "agent") b.add_conditional_edges("agent", route) b.add_edge("tools", "agent") # the loop-back arrow graph = b.compile(checkpointer=SqliteSaver(sqlite3.connect("cp.db", check_same_thread=False))) cfg = {"configurable": {"thread_id": "ticket-4471"}} graph.invoke({"messages": [{"role": "user", "content": q}]}, cfg) Same thread_id → same run. Different thread_id → a fresh, unrelated conversation. You must compile before use. What a checkpoint protects — and what it doesn’t Situation What happens on resume A node completed before the failure Not re-run. Docs: pending writes are stored “so that whenever we resume graph execution from that superstep we don’t re-run the successful nodes.” A node was in flight — crashed, or paused at interrupt() Re-entered at line one . Everything before the interrupt runs again. A side effect (charge, email, INSERT ) before the interrupt Happens twice. Docs: “side effects called before interrupt should (ideally) be idempotent.” A side effect after the interrupt, or in its own node Once. This is the fix, and it is design, not configuration. “Nothing is lost” and “nothing is repeated” are different promises. The framework makes the first one. Human in the loop from langgraph.types import interrupt, Command def approval(state: S) -> dict: ok = interrupt("Approve this action?") # raises; run is persisted and returns return {"approved": ok} graph.invoke(Command(resume=True), cfg) # ok == True, node restarts from the top A checkpointer is required — docs: “To use interrupt , you need: 1. A checkpointer to persist the graph state.” Never wrap interrupt() in a bare try/except — it works by raising, and the exception must reach the runtime. Multiple interrupts in one node are matched by index , so their order must be stable across re-runs. If none of the three is on your list, you have bought a dependency and an abstraction. Same shape as the agent-or-workflow rule : machinery is a price you pay for something specific. “We used a plain loop, because the run is 20 seconds and unattended” is a stronger interview answer than the library’s name. Glossary Superstep — one round of the graph: everything that runs before the next checkpoint is written. Reducer — the function attached to a state field saying how an update merges (append vs overwrite). Thread — one run’s history, addressed by thread_id . Its checkpoints are its timeline. Checkpoint — the saved state after a superstep. Durable execution — the property those checkpoints give you. Time travel — resuming from an older checkpoint instead of the newest, to replay or branch.
