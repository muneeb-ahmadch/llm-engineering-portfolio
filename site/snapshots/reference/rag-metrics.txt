Reference · RAG RAG evaluation metrics Formulas, thresholds, and the mistakes that show. Compressed from Day 16. Made to be reread the night before. Retrieval metrics These measure the vector search: not the answer. Diagnose here first: if retrieval missed it, the LLM never had a chance. MRR: Mean Reciprocal Rank Where does the first relevant chunk land? score(q) = 1 / rank_of_first_relevant_hit = 0 if no hit within top-k MRR = mean(score(q) for q in golden_set) Position of first hit 1st 2nd 3rd 4th 5th miss Score 1.0 0.5 0.33 0.25 0.2 0 Reading it: 1.0 perfect · 0.5 ≈ hit lands 2nd on average · 0.25 ≈ 4th · below 0.2 retrieval is broken. Two ways to get it wrong: dropping misses from the denominator (inflates a system that fails constantly); scoring a miss as 1/k instead of 0 . Blind spot: sees only the first hit. Says nothing about the rest of the set. NDCG: Normalized Discounted Cumulative Gain Are all the relevant chunks near the top? Reach for this when k > 5 and the whole retrieved set matters. DCG = Σ relevance(i) / log₂(i + 1) i = position IDCG = DCG of the ideal ordering (all relevant chunks first) NDCG = DCG / IDCG Worked: 5 retrieved, relevant at positions 1, 2, 5: DCG = 1/log₂(2) + 1/log₂(3) + 1/log₂(6) = 1.0 + 0.63 + 0.39 = 2.02 IDCG = 1/log₂(2) + 1/log₂(3) + 1/log₂(4) = 1.0 + 0.63 + 0.5 = 2.13 NDCG = 2.02 / 2.13 = 0.95 Reading it: > 0.8 good · < 0.6 relevant chunks are scattered. The log₂(i+1) denominator is the “discount”: a hit at position 10 is worth less than one at position 2, because that's how attention and context actually work. Recall@k Did we find it at all? The floor. Everything else is decoration if this is low. Recall@k = (# questions with ≥1 relevant chunk in top-k) / (# questions) Keyword coverage , the cheap variant, and the one worth having when your golden set carries keywords: coverage(q) = |keywords found in retrieved chunks| / |keywords required| # "Who won the IoT award?" keywords [Maxine, Thompson, IoT] # retrieved contain [Maxine, IoT] → 2/3 = 0.67 Coverage is a proxy — two blind spots Keyword coverage scores word overlap, not correctness , so it fails both ways. False negative: a chunk answers correctly in different words and scores 0 — the overfitting miss, where real definitions never use the exact phrase “validation accuracy.” False positive: a chunk carries the keywords but the meaning is wrong and still scores 1. Fine as a fast, free smoke test; useless for “did it actually answer .” When you need meaning, you need a judge — below. Precision@k Precision@k = (# relevant chunks retrieved) / k Usually not your problem. LLMs tolerate noise in context well, as long as the answer is in there. Only optimise precision when you're paying for context tokens, when the noise is actively misleading, or when context space is genuinely tight. Which metric, when Default pair: MRR + keyword coverage. Intuitive, cheap, and they track what users feel. Add NDCG when k > 5 and distribution across the set matters. Add precision only under cost or context-window pressure. Broad corpus (many topics, many ways to miss) → favour recall . Narrow corpus (one domain) → favour precision ; noise is the bigger risk. Answer quality: LLM-as-a-judge Retrieval metrics don't tell you if the answer was good. Exact string match is too strict (“Maxine Thompson won the award” ≠ “The award was won by Maxine Thompson”). Word overlap doesn't understand meaning. So: use a model to judge, on three dimensions, 1–5 each. Dimension Asks Fails when Accuracy Is the information correct? Wrong facts. Binary-ish, “2016” for “2015” is 1/5, not 4/5. Completeness Is anything necessary missing? “Maxine” when the reference says “Maxine Thompson” → 4/5. Relevance Is anything extra padded in? Unasked-for detail. “…She likes coffee.” → 3/5. The standard names — and the one the rubric above misses Accuracy/Completeness/Relevance is a homegrown judge. The industry-standard framing (from Ragas ) splits answer quality the same way, but names a dimension the rubric above has no column for: Standard name Asks Maps to Context precision / recall Did retrieval fetch chunks that contain the answer — judged by meaning, not keywords? the semantic version of recall@k / coverage Answer correctness Is the answer factually right vs ground truth? Accuracy Answer relevance Does it address the question without padding? Relevance Faithfulness Is every claim grounded in the retrieved context — or made up? no column above — the hallucination check Faithfulness is the one to remember. An answer can be accurate, complete, and relevant while stating a fact that appears in none of the retrieved chunks — true today because the model knew it from pre-training, wrong tomorrow when it doesn’t. Faithfulness grades the answer against its context , so an ungrounded claim fails even when it happens to be correct. It is the metric that catches the hallucination before it costs you. Rules that keep the judge honest: use a judge at least as strong as the generator; force structured output so scores parse cleanly; tell it explicitly “only give 5/5 for perfect answers” or it inflates everything; optionally few-shot it to calibrate. Cost: one call per test question. 150 tests on a mini-tier model is roughly $0.02–0.03. Local open-source judge is free. This is never the expensive part, there is no cost excuse for not evaluating. A worked baseline Day 16's system, for a feel for what these numbers look like in the wild. 1000-char chunks, MiniLM encoder, top-5: Metric Value Reading MRR 0.730 hits landing 2nd–3rd, not 1st NDCG 0.739 middling distribution Keyword coverage 83.8% missing ~16% of required terms Accuracy (judge) 3.99 sometimes wrong Completeness (judge) 3.85 leaving things out Relevance (judge) 4.57 at least not padding After tuning chunk size (500, top-10) and encoder ( text-embedding-3-large ): MRR 0.790 , accuracy 4.21 . Note the size of that win. Real, and modest. Anyone claiming RAG metrics near 1.0 is either overfitting the golden set or not measuring what they think. The rules underneath all of it There is no best technique. Your mileage will vary. Always measure, never assume. RAG is a performance optimisation , a similarity-search shortcut so you don't push the whole corpus through an expensive transformer. It is not a principled solution, which is exactly why it's empirical, why it fails in whack-a-mole fashion, and why the only real answer to “why did you choose that?” is a number.
