Chunking & the three misses

How to cut text so answers surface, and how to name a miss before you fix it. Compressed from Lesson 05. Made to be reread the night before.

When a golden question misses, it is one of three

Guessing which is the junior move. Two cheap looks turn the guess into a diagnosis: read the top-k, then grep the corpus.

MissWhat’s trueRead top-k?Grep corpus?Fix
Bent rulerAnswer is in the top-k; keyword rule scores it 0.Good chunk is there.—Judge by meaning: LLM-judge, context precision.
Ranking missAnswer exists in corpus but not in top-k.Nothing good.It’s there.Chunking, reranking, wider net, query rewrite.
Content gapAnswer is nowhere in the corpus.Nothing good.Empty.Add the document, or drop / rewrite the question.

The tell that’s easy to miss: the top-k read alone cannot separate a ranking miss from a content gap — both look like “no good chunk here.” Only the grep splits them. Skipping it is how you re-chunk a corpus that has no answer, or delete a question whose answer was there all along.

Why good answers rank low: dilution

A chunk’s embedding is the average of everything in it (cosine ranks by direction — see Lesson 02). One relevant line inside forty lines of code produces a vector pointing at the code, not the line. The answer isn’t missing — it’s outvoted. Better boundaries concentrate the signal so the chunk’s direction matches the query.

The splitter ladder — cheapest first

SplitterCuts onUse when
Fixed-sizeA character / token count.A throwaway baseline. Blind to structure — dilutes.
RecursiveParagraph → line → sentence → word, until it fits.The sane default for prose. Rarely cuts mid-thought.
Structure-awareThe document’s own markup: Markdown headings, HTML, code AST.Structured docs. Each chunk = one section.
SemanticEmbedding-similarity breakpoints between sentences.Unstructured text where topics drift with no headings. Costs embeddings up front.

Overlap (e.g. 10–15%) re-includes a few trailing chars/sentences in the next chunk so an answer split across a boundary survives in at least one piece. A patch for blind cutting — less needed once you cut on structure.

Keep the heading path as metadata

When you split on headings, attach the trail — file › H2 › H3 — to each chunk. Cheap at split time, expensive to reconstruct later. It buys: citations (“day26 § Monitoring Training says” beats “the docs say”), context for the generator, and metadata filters at query time. LangChain’s MarkdownHeaderTextSplitter returns it for free.

Special cases that break naive chunkers

  • Tables: keep whole; a half-table is worse than none. Consider one row-group per chunk with the header row repeated.
  • Code: split on function / class boundaries, never mid-block.
  • Lists & checklists: keep the list with its heading — the item is meaningless without “Signs of problems:” above it. (This is the exact overfitting failure.)

Defend it in one line

“There’s no universal chunk size — it’s a measured trade-off. I start with a recursive or structure-aware splitter matched to the document, keep heading metadata for citations, and I let the eval decide the size: a new splitter helps some questions and hurts others, so I ship the one that moves overall MRR, not the one that fixes a single query.”
