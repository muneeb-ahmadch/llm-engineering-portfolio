The pipeline, where the index lives, and what it costs

Retrieve → augment → generate; the vector-DB landscape; the cost and latency formulas. Compressed from Lesson 07. Made to be reread the night before.

The three stages

StageIsNot
RetrieveEmbed the query, rank chunks by similarity, keep the top-k. What Lessons 01–06 measured with MRR.Not an answer — just candidate text. A perfect retrieval score says nothing about what a generator does with it.
AugmentBuild the prompt: system instructions + retrieved context + the question, in one message set.Not optional glue — how the context is framed (told to say “I don't know” or not, ordered how) changes what the model does with good chunks.
GenerateOne LLM call, given the augmented prompt, producing the answer text. The only stage with real cost and real latency.Not deterministic even at temperature=0.0 across model versions — re-run before trusting a single generated answer as representative.
 
chunks   = retrieve_chunks(question)                 # stage 1, reuse eval's top-k, don't re-retrieve
context  = "\n\n".join(c["text"] for c in chunks)     # stage 2
messages = [{"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {question}"}]
response = client.chat.completions.create(model=ANSWER_MODEL, messages=messages, temperature=0.0)  # stage 3

Determinism & temperature

Retrieval is deterministic: embed → cosine-rank → top-k is arithmetic on fixed numbers, so the same query against the same corpus returns the same chunks every time. That's why MRR/coverage/misses can gate every commit — a drop between two runs of identical code is a real regression, not noise. Generation is a different animal: an LLM emits one token at a time from a probability distribution over the vocabulary, and temperature controls how that distribution is sampled.

TemperatureSampling behavior
0Always take the single highest-probability token (argmax). No randomness by design — same prompt in, same text out, run after run.
1 (default)Sample proportionally to the model's own probabilities — a genuine weighted random draw. Same prompt can yield different wording, or a different fact included/omitted, on every call.
>1Flattens the distribution further — lower-probability tokens become relatively more likely. More variety, more risk of incoherence.

gpt-5.6-luna rejects temperature=0.0 outright (“Only the default (1) value is supported”) — there is no dial to turn off. Every call samples from the full distribution, so generated answers vary run-to-run even with identical code and identical retrieval. That's the concrete reason a content-based CI gate on generated text would flake, and why Lesson 07 splits the pipeline: deterministic retrieval metrics on every commit, non-deterministic priced generation nightly. Note that even temperature=0.0 on other models isn't a perfect guarantee across model versions or hardware — but a model forced to temperature=1 is a much larger, deliberate source of variance, not a rounding-error edge case.

Where the index lives

StoreTierAdds over brute-force numpy
Plain array + cosineDev / learningNothing — exact search, zero infra. Correct choice under a few thousand chunks.
ChromaDev → small prodSQLite persistence, metadata filtering, a real client API.
FAISSPrototyping at scaleVery fast in-memory search; no persistence by default.
pgvectorSmall → medium prodVectors inside Postgres you already operate — no new database.
Pinecone / WeaviateLarge-scale prodManaged, sharded, built for billions of vectors.

The load-bearing line (Day 15 lecture notes, verbatim): “Remember: the encoder choice matters much more than the database choice!” At a scale where exact search is still fast — low thousands of chunks — a numpy array and Chroma return identical nearest neighbours. The gap only opens once a store switches to approximate search (HNSW) to stay fast at millions of vectors, trading a sliver of recall for speed. Don't claim a database you haven't needed yet.

Cost, defined

cost = (usage.prompt_tokens     / 1_000_000) * input_price_per_million
     + (usage.completion_tokens / 1_000_000) * output_price_per_million

Token counts come off the real API response — never estimated from character count once you have a live call. Prices come from the vendor's current published rate, checked the day you run it, not a remembered number from a lecture or a prior session: model pricing tables change, and the exact model a course notebook hardcodes can rotate off the current page entirely (it did, mid-course, for this one — see Lesson 07).

Latency, defined

Time only the generation call — wall-clock around client.chat.completions.create(...) itself, the same way embed_secs already isolates embedding time from the rest of the pipeline. Conflating retrieval and generation latency hides which stage actually dominates a real deployment's response time (generation, almost always, by a wide margin).

Defend it in one line

“Retrieval, augmentation, and generation are three separable stages — I measure retrieval quality with MRR independent of any LLM, then add a real, priced, timed generation call on top once retrieval is trustworthy. I keep the vector store as the simplest thing that's provably equivalent to a real database at my scale, and I price every generation run from the vendor's current rate, checked the day I ran it — not a number I remembered.”
