Injection & guardrails

The one attack a RAG agent uniquely exposes, why the faithfulness score can't see it, and the three defences you can build from parts you already own. Compressed from Lesson 12. Made to be reread the night before an interview.

Prompt injection: LLM01, the two flavours

Definition (OWASP 2025): “A prompt injection vulnerability occurs when user prompts alter the LLM's behavior or output in unintended ways.” The input can affect the model even if imperceptible to a human.

Where the instruction comes fromThe RAG-agent case
DirectThe user's own prompt changes behaviour.Lower risk if you own the prompt template.
IndirectExternal content: a file, a page, a retrieved chunk, is interpreted as instructions.The live one. Any corpus you don't write yourself is an attack surface.

Why an agent exposes it more than a fixed chain

A fixed chain reads a chunk once and answers. An agent reads a chunk, decides its next action from what the chunk said, and loops. That loop-back arrow: the thing that made it an agent, is the thing that turns retrieved text into instructions the model can act on. The model cannot distinguish a fact in the context from an order in the context; it is all tokens.

The trap: faithfulness is blind to injection

The one durable idea

Faithfulness measures grounding; injection is grounded by construction. A judge that asks “did the answer come from the context?” passes an attack that writes the answer into the context. Hallucination = the model reaching past the context. Injection = the model faithfully following a poisoned context. Same-looking answer, opposite wound, different control. Reaching for the guard you already own is the reflex to resist.

Diagnose before you defend: the RAG-agent threat model

Least privilege (OWASP) and “add complexity only when it demonstrably improves outcomes” (Anthropic) point the same way: defend the category your architecture actually exposes, and prove the defence moves a number.

OWASP riskWhat it isHandled by…
LLM06 Excessive AgencyTools that can act: write, pay, send, delete, reached on a path you didn't foresee.Least privilege: grant read-only / local tools. A read tool is a different risk class from a writing one.
LLM10 Unbounded ConsumptionA loop that bills forever. The only agent failure that shows up on a credit card, not in an output.Two caps, not one: MAX_STEPS bounds calls; a client timeout bounds time. A step cap alone leaves a hung call unbounded.
LLM01 Prompt InjectionRetrieved/external content interpreted as instructions.The three defences below. Not covered by grounding.
LLM02 Sensitive DisclosureSecrets in the corpus leaking into answers.Live only once the corpus is private. Name it, park it.

The three defences worth building, OWASP LLM01 mitigations

Mitigation (OWASP verbatim)ConcretelyCeiling
#6 Segregate External Content, “separate and clearly denote untrusted content.”Wrap each retrieved chunk in a delimiter; instruct: delimited text is data to read, never instructions to obey.First cut, not a fix. A subtle injection that doesn't announce itself walks through.
#2 Define Output Formats, “request reasoning and source citations, and use deterministic code to validate.”Structured output {answer, cited_chunk_ids}; then Python checks every claim traces to a real, non-poisoned chunk.Only as good as the validator. The model can still cite the poisoned chunk.
#7 Adversarial Testing, “treat models as untrusted users.”An injection set, poisoned questions whose correct behaviour is to refuse the order. Your trap-set methodology, one file over.Measures the attacks you thought of. Absence of failure ≠ proof of safety.

The other four OWASP mitigations, worth naming in an interview but not building today: constrain model behaviour (strict role in the system prompt), privilege control (“handle functions in code rather than providing them to the model”), human-in-the-loop for high-risk actions, and input/output filtering (semantic filters; the RAG triad).

Guardrails as boundary tripwires: the Day 20 shape

@input_guardrail   # runs BEFORE the agent, segregate / filter the request
@output_guardrail  # runs AFTER  the agent, validate citations before shipping
  • A guardrail returns a tripwire: if triggered, an exception halts the run and the trace shows which guard fired.
  • Guardrails sit only at system boundaries, entry and exit. You cannot place one mid-loop, which is exactly where the poisoned chunk enters. So: segregate on the way in, validate citations on the way out.
  • Structured output (Pydantic output_type / response_format) is what gives the output guardrail something deterministic to check. Prose gives you nothing to validate in code.

The honest interview answer

“I ran an indirect injection against my own RAG agent, a poisoned chunk carrying an order. It obeyed. Then I measured that my faithfulness guard scored the answer grounded, because the malicious claim was in the context by construction. So I added content segregation and a cited-chunk validator, built a small injection set, and measured the block rate, here's the number, and here's the injection that still gets through.”

The weak answer is “we added guardrails.” The strong one names the specific attack, the specific reason the obvious guard failed, and the number the fix moved: the same shape as every verdict in this course.
